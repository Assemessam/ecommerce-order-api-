# OpenAPI 3.1 and interactive API documentation

Scramble 0.13.47 generates the API specification from Laravel's routes, controllers, Form Requests, and API Resources. The project applies targeted documentation transformations for contracts that inference alone cannot express: the API error envelope, DTO-backed cart fields, conditional order summaries, strict JSON inputs, header-only checkout, and business errors. These changes describe the existing API; they do not change authentication, permissions, transactions, schema, or business behavior.

The document uses OpenAPI 3.1 and contract metadata version `1.0.0`. That version identifies the documented contract; it does not introduce a version prefix into the existing routes. Functional groups are Health, Authentication, Products, Cart, Cart Promotions, Checkout, Orders, Admin Products, and Admin Promotions. The exported source is [openapi.json](openapi.json), generated by Scramble rather than maintained as a second independent contract.

## Start Docker and open the documentation

For an existing installation with dependencies, a configured `.env`, and an application key:

```bash
docker compose up -d api
```

For a new installation, use the [root installation guide](../README.md#installation-and-database-setup). Preserve an existing `.env` and nonempty application key. Apply normal additive migrations when installing the application; do not reset the development database or remove persistent volumes. Documentation requires the application's PostgreSQL schema because Scramble reads model column metadata during inference. The dedicated project Redis service remains required for API rate limiting.

At the default `APP_PORT=8091`:

- Interactive Stoplight Elements interface: **http://localhost:8091/docs/api**.
- Generated OpenAPI JSON: **http://localhost:8091/docs/api.json**.
- Committed export: [docs/openapi.json](openapi.json).

Use the configured `APP_PORT` when it differs. The specification declares a relative `/api` server, so the interactive interface uses its actual origin, scheme, and port. OpenAPI path keys omit the `/api` prefix; combining the server and path yields the original Laravel URL. API behavior never hardcodes port 8091.

The UI's JavaScript and CSS load from the CDN configured by Scramble's maintained Elements renderer. Browser rendering requires access to those assets. A successful HTTP response containing HTML establishes route availability; it alone does not establish successful browser rendering or a completed Try It Out request.

## Bearer authentication and administrative access

1. Open **Authentication** and submit a valid registration or login request.
2. Copy the returned `data.token` from the successful response.
3. Open an authenticated operation and enter **only the token**, without `Bearer `, into the bearer authentication input.
4. Use **Try It Out**. The interface supplies `Authorization: Bearer <token>`.

Registration/login also return `data.user` and `data.token_type: "Bearer"`. `/api/auth/me` returns the user directly inside `data`. User resources contain only `id`, `name`, `email`, `created_at`, and `updated_at`. Logout revokes the current token and returns 204 without a body. No cookie session or CSRF token is required for these bearer requests.

Five operations are public: health, registration, login, product listing, and product detail. The remaining twenty require Sanctum. Middleware-aware documentation assigns bearer security to protected routes and explicitly marks public operations with empty security requirements. Role names are operational RBAC roles, not OAuth scopes.

Ordinary authenticated users can operate on their own cart and orders. Staff roles do not grant access to another customer's records. Administrative operations check the current permissions on every request:

| Administrative action | Required permission | Provisioned roles |
| --- | --- | --- |
| List/read products | `products.view-admin` | `administrator`, `product_manager` |
| Create products | `products.create` | `administrator`, `product_manager` |
| Update products | `products.update` | `administrator`, `product_manager` |
| Include `stock_adjustment` in product PATCH | Also `inventory.adjust` | `administrator`, `product_manager` |
| List/read promotions | `promotions.view-admin` | `administrator`, `promotion_manager` |
| Create promotions | `promotions.create` | `administrator`, `promotion_manager` |
| Update promotions | `promotions.update` | `administrator`, `promotion_manager` |

Provision an existing local account through the existing Artisan command, then log in with that account's private credentials:

```bash
docker compose exec -T api php artisan roles:grant your-staff@example.test administrator --no-interaction
# For a narrower role, use product_manager or promotion_manager instead.
```

Provisioning requires `APP_ENV=local`. No role-assignment or special administrator-registration REST endpoint exists. Existing tokens reflect later permission grants or revocations. Keep tokens and credentials in local UI/Postman values; do not save them in the committed specification.

## Documentation access restrictions

Scramble's supported documentation middleware protects both `/docs/api` and `/docs/api.json`. The project admits only `APP_ENV=local`. Testing, staging, and production return 403, independently of `APP_DEBUG`, authentication, or an administrator role. Changing API bearer security cannot unlock these documentation routes. The committed contract can be read publicly because it contains safe examples and API descriptions, not runtime credentials or private infrastructure values.

CLI export remains available to development and CI; it does not make HTTP documentation routes accessible in CI's testing environment. Authentication and authorization middleware on the business routes remain unchanged.

## Complete API, Postman, and OpenAPI comparison

The source of truth is [routes/api.php](../routes/api.php), the linked controller methods, Form Requests, API Resources, services, and [bootstrap/app.php](../bootstrap/app.php)'s exception mapping. [The Postman collection](../postman/Ecommerce_Order_Promotion_API.postman_collection.json) contains 80 requests across 12 folders; repeated workflow and error requests normalize to the same 25 operations. Its response contracts are executable assertions, rather than saved response examples. The generated specification has each operation exactly once. HEAD aliases, `/up`, and documentation routes are excluded from business-operation coverage.

Controller names below are in `App\Http\Controllers\Api` and omit the `Controller` suffix. **Bearer** means a current Sanctum token; **Product permission** and **Promotion permission** include that bearer requirement plus the action-specific permission above. Every business operation also documents **429** for its existing Redis rate limit and **503** when Redis admission is unavailable. ## Request constraints and examples

Nine operations accept JSON request bodies. The specification includes safe examples for each, including separate percentage and fixed promotion examples. Runtime Postman emails, passwords, tokens, generated IDs, and dates are not copied into the export. Checkout, logout, cancellation, all DELETE operations, and all GET operations have no invented JSON body.

Registration requires `name`, `email`, `password`, and matching `password_confirmation`; `device_name` is optional. Names/emails are bounded to 255 characters; email normalizes to lowercase. Registration passwords require at least 12 characters, mixed case, a digit, and a symbol, with the existing 72-byte/null-byte safeguards. Login requires email/password and accepts an optional device name without imposing new registration strength rules on existing credentials. Device names are limited to 100 characters.

Product queries accept `search`, `min_price`, `max_price`, `available`, `sort`, `direction`, `page`, and `per_page`. Search is an optional nullable, trimmed string of at most 100 characters, interpreted as a literal case-insensitive substring of name, SKU, or description. Price bounds are inclusive nonnegative integer minor units, with maximum no lower than minimum. `available=true|false` filters positive/zero stock. Sorting permits `name|price|created_at` and `asc|desc`; defaults are `created_at desc`, with an ID tie-breaker. Pagination defaults to page 1 and 15 entries, caps `per_page` at 100, and bounds page to 2147483647. Administrative product queries add `status=active|inactive`; absent status includes both. Promotion queries accept pagination and `is_active=true|false`; order history accepts pagination only and always sorts newest first. Query inputs come from the URL, so a GET body cannot override filters.

Path IDs identify products, promotions, cart lines, or orders as shown in the matrix. An item URL uses the cart-line ID rather than the product ID. Route constraints require numeric IDs; invalid, zero, overflowing, missing, or foreign resource identifiers resolve to the existing 404 behavior. Ownership always comes from the bearer token.

Cart item creation requires positive actual JSON integers for `product_id` and `quantity`; PATCH requires a positive actual JSON integer replacement `quantity`. Strings, floats, and booleans are rejected. POST adds to an existing quantity; PATCH replaces it. Cart promotion application accepts the normalized `code`, using the same canonical code constraints as administrative promotion creation. Cart estimates do not reserve stock or consume promotion usage.

Product creation requires `name`, `sku`, and `price_minor`. Optional `description` is nullable and at most 10000 characters; `stock_quantity` defaults to 0; `status` defaults to `active`. Name/SKU are trimmed and at most 255 characters; SKU is canonicalized and unique. Money and stock use nonnegative actual JSON integers through PHP's supported signed integer maximum. Product PATCH omits absolute `stock_quantity` and accepts signed nonzero `stock_adjustment` instead: this is a relative change, such as `-2` or `3`. Omitted fields retain their previous values; explicit null clears only nullable `description`. Repeated stock adjustment repeats the delta, so it is not idempotent. Supplying the create-only/update-only stock field in the wrong operation returns 422 even when null.

Promotion creation requires `code`, `type`, and `value`. The canonical code is `[A-Z0-9][A-Z0-9_-]{0,63}` after trimming and uppercasing. Types are `percentage` and `fixed`. Percentage values are basis points, so `1000 = 10%`, with range 1–10000. Fixed values are positive integer minor units. Optional `minimum_cart_amount_minor` defaults to 0; nullable `maximum_discount_minor`, `global_usage_limit`, and `per_customer_usage_limit` must be positive integers when present. `is_active` is an actual JSON boolean and defaults to true. `starts_at`/`expires_at` accept null or ISO 8601 timestamps with an explicit offset, whole seconds or exactly six fractional digits; `Z` is accepted. Start must precede expiration when both exist.

Promotion PATCH makes creation fields optional. Missing values retain the stored value; explicit null clears caps, date bounds, and usage limits. Combined type/value and validity constraints are evaluated against the retained fields. Non-null limits cannot be reduced below consumed usage. Past orders and usage records retain their historical snapshots.

Checkout accepts only the optional `Idempotency-Key` header: 1–128 case-sensitive ASCII characters, starting with a letter/digit and continuing with letters/digits/period/underscore/colon/hyphen. A successful key is customer-scoped and permanently replays its original order with 200, even after cancellation or cart refill. Use a new key for a new purchase; preserve a key when retrying an uncertain result. There is no checkout JSON payload or payload fingerprint. Cancellation accepts no body, transitions `placed` to `cancelled`, and restores inventory once; a valid repeat returns the same cancelled order with 200.

## Response shapes and errors

Success resources use `data`; lists add Laravel pagination `links` and `meta`. Status 204 has no response body. IDs, quantities, minor money amounts, and basis-point values are integers. Nullable values and conditionally omitted properties remain distinct. Resource timestamps are ISO 8601 strings with their actual nullability.

- **Product:** ID, name, SKU, nullable description, `price` money object, stock quantity, `active|inactive` status, and timestamps. Administrative products use the same resource.
- **Cart:** nullable ID for an unpersisted empty cart, item array, subtotal, nullable promotion and eligibility, estimated discount, and estimated total. Cart items contain the product, quantity, unit-price/line-subtotal money objects, and availability fields including nullable reason.
- **Cart promotion:** percentage basis points or fixed money amount, minimum/cap money wrappers, and nullable validity bounds. The inapplicable percentage/fixed representation is null.
- **Order:** customer ID, `placed|cancelled` status, stored currency/totals, nullable historical promotion snapshot, purchase/audit timestamps, and cancellation/restoration timestamps. Summary lists omit `items`; checkout/detail/cancellation include stored item snapshots containing product ID/name/SKU, quantity, and integer unit-price/line-subtotal fields. They do not read current catalogue prices into historical orders.
- **AdminPromotion:** editable raw `value`, minor-unit minimum/cap fields, validity dates, nullable usage limits, boolean active state, aggregate `redemptions_count`, and timestamps. It does not reuse the differently shaped customer cart promotion resource.

Error JSON is `{"error":{"code":"…","message":"…","request_id":"…","details":{}}}` with `details` present only where the application supplies it. Validation has `details.fields`, mapping field names to message arrays. Insufficient stock includes integer `details.product_id` and `details.available`. Errors preserve the request ID; the API applies its existing `X-Request-ID` and no-store headers.

Important 409 codes include `INSUFFICIENT_STOCK`, `PRODUCT_INACTIVE`, `CART_CONFLICT`, `CART_TOTAL_TOO_LARGE`, `CART_EMPTY`, `CHECKOUT_CONFLICT`, promotion usage exhaustion, `INVENTORY_ADJUSTMENT_CONFLICT`, `PROMOTION_USAGE_LIMIT_CONFLICT`, and cancellation conflicts. Unknown promotions return 404; inactive, not-started, expired, or minimum-not-met promotions return 422; empty/invalid carts and exhausted usage return 409. Missing/foreign orders return indistinguishable 404 responses. Administrative authorization returns 403. Rate limiting returns 429 with `Retry-After`, while Redis admission failure returns 503 before business mutation. The 400 entries in the matrix describe the actual public rate limiter's malformed-client-IP admission handling, not an invented JSON-body rule on every endpoint.

## Export, validation, and CI

Regenerate the committed contract after API changes:

```bash
docker compose exec -T api php artisan scramble:export --path=docs/openapi.json --fail-on-unknown --no-interaction
docker compose exec -T api php artisan test --compact tests/Feature/OpenApiDocumentationTest.php
git diff -- docs/openapi.json
```

`--fail-on-unknown` makes unresolved inference a failure. Relative server metadata makes generation independent of a developer's host/port. Repeated generation without contract changes must produce the same JSON. Review the generated diff alongside route, Form Request, Resource, and error-handler changes; never fix staleness by hand-editing an independent specification.

[The focused Pest tests](../tests/Feature/OpenApiDocumentationTest.php) check local documentation access, denial in nonlocal environments, OpenAPI 3.1 structure/internal references/typed schemas, exact 25-operation Laravel/Postman coverage, bearer/public security, headers/query/path inputs, bodyless operations, request examples, success/error statuses, safe exported content, deterministic generator/export equality, and representative live API response schemas. These checks use the project's real PostgreSQL/Redis testing configuration. They do not introduce a second generator or a separate Node/Python validator dependency.

`phpunit.xml` gives the test runner a 512 MB memory budget because Scramble's static inference also runs inside the regression process. The default 128 MB budget was exhausted during full-suite verification. This setting applies to PHPUnit/Pest; it does not change the application's PHP memory limit.

[The GitHub Actions workflow](../.github/workflows/ci.yml) runs its OpenAPI gate in the committed PHP 8.5 Docker runtime. Before generation it applies migrations only to `ecommerce_order_api_test`, then exports with strict inference, runs the focused suite, and executes `git diff --exit-code -- docs/openapi.json`. A changed export fails the gate rather than creating a commit. The existing full regression suite follows sequentially, including all seven concurrency suites. OpenAPI logs/JUnit results join the existing artifacts and job summary.

For complete local verification:

```bash
docker compose exec -T api composer validate --strict
docker compose exec -T api composer audit --locked
docker compose exec -T api vendor/bin/pint --dirty --format agent
docker compose exec -T api php artisan route:list --path=api --except-vendor --no-interaction
docker compose exec -T api php artisan test --compact
docker compose config --quiet
git diff --check
```

Run database suites sequentially; the existing guards require Compose PostgreSQL `postgres:5432`, database `ecommerce_order_api_test`, and isolated project Redis databases/namespaces. Do not use SQLite, `--parallel`, concurrent test invocations, development-database resets, volume deletion, or unrelated containers such as `postgres-local`. The [root test guide](../README.md#tests-and-quality-checks) contains the separate concurrency command. The application database is not a test target.

## OpenAPI and Postman responsibilities

OpenAPI supplies a browsable, exportable contract for all operations. Postman retains its ordered customer/administrator workflow, dynamic variables, replay/cancellation checks, and negative scenarios. Both derive their claims from the working API. Documentation accuracy checks supplement the existing business, database, authorization, and concurrency tests; they do not replace them. Schema examples demonstrate format and meaning, while valid promotion windows, available stock, ownership, current permissions, and uniqueness still determine whether an interactive request succeeds.
